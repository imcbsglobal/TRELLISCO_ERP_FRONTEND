## System / Approach

This is a standard Vite + React SPA managed with **npm** (Node Package Manager). Dependencies are declared in `package.json` and resolved/locked by `package-lock.json`. There is no vendoring, no private registry configuration, and no monorepo tooling — a single flat project.

## Key Files

- `package.json` — the sole manifest declaring runtime and dev dependencies, plus npm scripts (`dev`, `build`, `lint`, `preview`).
- `package-lock.json` — the generated lockfile pinning exact transitive dependency versions for reproducible installs.
- `.gitignore` — excludes `node_modules/` and `dist/` from version control (so only manifests and lockfiles are committed).

No `.npmrc`, `.yarnrc`, `pnpm-workspace.yaml`, or similar registry/auth config files exist in the repository root.

## Architecture & Conventions Observed

- **Dependency categories**: Runtime libraries live under `dependencies` (`axios`, `matter-js`, `ogl`, `react`, `react-dom`, `react-router-dom`); build/tooling tools live under `devDependencies` (`vite`, `@vitejs/plugin-react`, `eslint*`, `sass-embedded`, `@types/react*`).
- **Version ranges**: All entries use caret (`^`) semver ranges, allowing minor/patch upgrades within the major version (e.g. `react: ^19.2.8`, `vite: ^8.3.0`). No exact pins in the manifest; exact pins are delegated to `package-lock.json`.
- **Package manager**: npm is used exclusively — there is no `yarn.lock`, `pnpm-lock.yaml`, or `bun.lock` present. The presence of `package-lock.json` confirms npm as the resolver.
- **Private registries**: None configured. No `registry`, `@scope:` registry overrides, `npm_config_registry`, or `NPM_CONFIG_REGISTRY` variables were found anywhere in the repo. Packages resolve against the default public npm registry.
- **Vendoring**: No vendored third-party code under source directories; all third-party code is pulled into `node_modules/` at install time.
- **Scripts as entry points**: `npm run dev` / `npm run build` / `npm run lint` / `npm run preview` are the documented commands for working with the dependency tree.

## Constraints / Rules

- No explicit rule enforcing pinned versions in `package.json`; the convention is to use `^` ranges and rely on `package-lock.json` for deterministic builds.
- No private registry or authentication tokens are checked into the repository (none found), so all packages come from the public npm registry.
- `node_modules/` is gitignored, meaning dependency resolution happens locally during development and CI — the lockfile is the source of truth for installed versions.
